# to-spec 轻量评估量表

本量表用于人工或自动对比 Skill 改动前后的对齐质量。先跑无 Skill 指引的控制组，再跑当前 `to-spec`；复杂案例可重复 3 次观察稳定性。不要把评估过程写入业务 spec。

## 质量维度

每项 0-2 分：0 为缺失或明显错误，1 为部分满足，2 为稳定满足。

| 维度 | 2 分标准 |
| --- | --- |
| 底座质量 | 明确根问题、成功边界、不变量、系统 / 权威边界和非目标，且有仓库证据支撑。 |
| 实质决策召回 | 会改变行为、数据、权限、契约、重大 scope 或验收的分叉均被识别。 |
| 归属准确性 | 仓库事实、用户决策、Agent 决策、runtime 选择和外部未知分类准确。 |
| 避免错误提问 | 不向用户询问可查事实、普通工程判断或执行时细节。 |
| 依赖顺序 | 先关闭能解锁多个下游判断的根问题，不提前追问依赖项。 |
| 推荐质量 | 人类问题包含明确建议、关键理由、主要影响和解锁范围。 |
| 就绪证明 | 能具体证明实现无需猜核心口径；实质未知存在时不会误报 ready。 |
| artifact 质量 | 只保存稳定结论与真实开放问题，无问答流水、决策树或 runtime 拓扑。 |

## 效率指标

除质量分外记录：

- 用户问题总数，以及其中真正属于人类决策的问题数。
- 首个问题是否命中决策前沿。
- 完成对齐的总 token、墙钟时间与对话轮数。
- 实现阶段因 spec 缺口导致的返工或重新询问次数。
- 是否为了简单工作错误创建 spec，或为了复杂工作错误直接开工。

效率不能以漏掉实质决策为代价。优先比较“达到同等或更高质量时”的问题数、token、时间和返工。

## 失败信号

- 象征性列出几个通用问题，却没有确认成功 / 失败边界或权威来源。
- 让用户决定代码组织、工具、子代理、测试命令等 Agent / runtime 范围内容。
- 未查仓库便询问现状，或忽略现有证据冲突。
- 把设计过程、问题树或 rejected branches 长期写入 spec。
- 用完整模板掩盖关键未知，或在外部契约 / 数据语义未确认时标记 ready。
- 为追求少问而擅自决定产品、权限、风险或不可逆选择。
