# to-align 轻量评估量表

本量表用于判断 `to-align` 是否在正式编码前完成必要对齐，同时避免把低概率边角扩成无限流程。先跑无 Skill 控制组，再跑当前 Skill；不要把评估过程写入业务 spec。

## 质量维度

每项 0-2 分：0 为缺失或明显错误，1 为部分满足，2 为稳定满足。

| 维度 | 2 分标准 |
| --- | --- |
| 原始覆盖 | 每个原始 requirement 都有 confirmed、defaulted、用户接受的 deferred 或明确 blocker。 |
| 事实优先 | 先查仓库、文档和运行证据，不向用户询问可查事实。 |
| 决策前沿 | 先关闭会解锁下游的根问题；同一前沿的少量独立决策可合并，不机械逐题。 |
| Authority | 只把产品、权限、不可逆和风险接受交人类；工程与 runtime 选择由 Agent 处理。 |
| ROI | 真实事故和高影响失败有恢复；低概率有限影响边角采用简单保护或明确暂缓。 |
| 收口 | 以 ready 或 blocked-and-stop 结束，不重复追问、无限扩展或误开工。 |
| 职责边界 | `to-align` 不改产品代码或创建 artifact；稳定结论和 readiness 委托 `to-spec`。 |
| 授权范围 | 对齐后直接实现的授权只覆盖当前 active goal 和当前 scope。 |
| 只读降级 | 无 spec 写权限时仍能报告 unpersisted 终态，并使陈旧 readiness 失效。 |

## 效率指标

- 覆盖全部原始 requirement 所需轮数。
- 人类问题中真正属于 human-owned 实质决策的比例。
- 重复问题、无新证据追问和低影响边角讨论次数。
- 因遗漏兼容、恢复、验收或 authority 边界导致的实现返工次数。
- ready 后是否立即停止；blocked 后是否给出一次性解除条件。

## 失败信号

- 未完成原始需求覆盖就开始修改产品代码。
- 把可查仓库事实、普通工程结构或执行细节交用户决定。
- 为理论故障增加复杂状态机、永久 sidecar、长迁移链或大量问题。
- Agent 未经用户接受便 deferred 原始 outcome。
- blocker 没有新证据仍反复追问，或为了结束而误报 ready。
- `to-align` 与 `to-spec` 重复启动对齐、重复提问或保存问答流水。
- 需求范围已变化仍沿用历史“开始实现”授权。
- 因不能写 spec 而无限对齐，或继续信任已被新 scope 推翻的旧 readiness。
