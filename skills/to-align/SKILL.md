# to-align

`to-align` 是正式编码前的多轮对齐入口。它维护对话中的需求覆盖与决策前沿，直到实现者不再需要猜测核心口径；稳定结论交给 `to-spec`，不创建新的 alignment artifact，也不保存问答流水。

进入本 Skill 后，先完整读取同级 `../to-spec/SKILL.md`。`to-align` 负责持续对齐的生命周期和停止条件，`to-spec` 继续负责 spec、readiness 与 Progress 的规范性写入。嵌套调用 `to-spec` 时传递当前覆盖结论，只做覆盖写入与就绪校验；除非发现矛盾或核心缺口，不重新启动一轮对齐或重复提问。

## Quick Path

1. 暂停产品代码修改；允许只读取证、运行无副作用检查，以及在用户已授权时更新 spec。
2. 确定 `SKY_FLOW_ROOT`、语言、现有 spec，以及用户是否已对当前 active goal 和当前 scope 明确授权“对齐完成后直接实现”。
3. 从用户原始要求、仓库事实、近期变更、现有文档和真实运行证据建立需求覆盖表。
4. 新 scope 使现有 `Ready: yes` 失效时，已授权写 spec 就立即调用 `to-spec` 改为 `Ready: no` 并记录当前 blocker；只读场景明确标记旧 readiness 已过期，不允许据此进入实现。
5. 先统一目标、成功 / 失败边界、不变量、系统所有权、兼容与明确非目标。
6. 把未知分为仓库事实、人类决策、Agent 决策、runtime 选择和外部未知；仓库事实先查，不转问用户。
7. 沿当前最有下游影响的决策前沿推进；同一前沿内互不依赖的少量人类决策可以合并询问，每项都给出推荐、主要影响和它会解锁的范围。
8. 每轮把已确认、已调整、采用默认值、明确暂缓和仍开放的问题压缩回覆盖表；新增需求只重算受影响部分。
9. 稳定结论达到长期保存价值且用户已授权写 spec 时调用 `to-spec` 覆盖写入；只读场景在对话中保留紧凑结论并标记 `unpersisted`。不要把问题树、聊天轮次或临时方案写进 spec。
10. 满足停止条件后使用 `to-spec` 的就绪证明判定；授权写入时同步持久化。只有 `ready` 且用户已授权继续实现时才交给 `to-implement`；`blocked-and-stop` 记录解除条件后停止，其余 ready 场景停在编码 gate 前。

## 对齐工作集

对话中维护一个轻量覆盖表，按原始 requirement 或独立 outcome 编号。每项只保留当前结论：

- `confirmed`：外部行为和成功标准已确认。
- `defaulted`：属于 Agent 边界内，已给出有依据的默认设计。
- `deferred`：用户明确接受原始 requirement 不属于本轮，或 Agent 暂缓后来发现、且不改变原始 outcome 的可选边角；记录恢复条件或残余影响。
- `open`：仍会改变设计的实质问题。
- `blocked`：依赖外部证据、权限或人类决定，当前不能证明 ready。

只检查与任务有关的维度，不机械填模板：

- 目标、成功 / 失败定义和非目标。
- 发起方、状态 owner、最终裁决方和影响边界。
- 外部接口、数据语义、权限、安全、兼容、迁移与回滚。
- 正常路径、可信的失败恢复路径和可验证证据。
- 会影响时间、成本、发布或真实设备验收的约束。

覆盖表只存在于 runtime；跨压缩需要保留的稳定事实由 `to-spec` 写入 spec。

## 实质性与决策归属

答案不同会改变以下任一项时，才把问题提升到对齐前沿：

- 成功标准或用户可观察行为。
- 状态所有权、数据语义、一致性或权限边界。
- 兼容、迁移、回滚、重大 scope 或不可逆风险。
- 验收口径、发布策略或需要人类接受的残余风险。

处理方式沿用 `to-spec`：

- 仓库事实：继续取证，不能用提问代替调查。
- 人类决策：给出推荐后询问，不替用户接受产品或风险口径。
- Agent 决策：在已确认边界内直接判断，说明关键依据与取舍。
- runtime 选择：留给实现期，不进入 spec。
- 外部未知：记录 owner、影响与解除条件；实质阻塞则保持未就绪。

## 多轮推进

每轮只推进最靠近根部的开放前沿。用户回答后立即判断哪些依赖问题已自动关闭，不按预先生成的问题清单机械追问。同一问题没有新证据时不重复询问：Agent-owned 事项采用有依据的默认值；human-owned 事项保持 blocker 并结束本轮对齐。

用户更新需求时：

1. 将新要求映射到原覆盖项或新增 outcome。
2. 标出它推翻的结论、兼容边界和验收变化。
3. 只重新打开受影响的实质决策。
4. 让 `to-spec` 覆盖更新稳定真相，不追加聊天时间线。

复杂任务可在每轮用以下紧凑形状反馈，但不必机械展示所有栏位：

```text
本轮确认：<稳定结论>
发生调整：<被新证据或用户决定改变的点>
默认 / 暂缓：<Agent 默认与明确非目标>
仍需决定：<当前前沿；无则写无>
```

## ROI Guard

对齐质量不以问题数量、覆盖理论边界或代码量衡量。优先保护高概率、高影响、跨系统、兼容与不可逆风险。

- 已有真实事故、常见失败或会造成持续停服 / 数据错误 / 权限突破的路径必须明确兜底。
- 低概率且影响有限的场景优先使用简单保护、日志、有限重试或明确重建。
- 不为缺少证据的理论风险设计复杂状态机、永久 sidecar、长迁移链或巨量代码。
- 若保护成本明显高于风险，明确采用简单方案或暂缓，并把可接受残余风险写入 spec。
- 只有风险接受权属于用户时才询问；普通工程取舍由 Agent 决定。

当讨论开始重复、只改变内部实现细节或不断产生更小边角时，立即回到成功边界与停止条件，不继续扩展问题树。

## 停止条件

对齐只有两个终态，达到任一终态就停止，不因 blocker 无限循环：

- `ready`：每个原始 requirement 都是 `confirmed`、`defaulted` 或经用户明确接受的 `deferred`；没有会改变外部行为、数据、权限、兼容、重大 scope 或验收的开放人类决策；实现者无需猜测产品口径。
- `blocked-and-stop`：剩余实质问题依赖外部证据、权限或人类决定，当前无法继续；记录 blocker、owner、影响和解除条件，不重复追问。

两种终态都要求失败恢复与真实风险相称、验证意图能区分“已经实现”与“看起来可用”，并使用 `to-spec` 的规则形成对应就绪证明。用户授权写 spec 时持久化；只读或不可写时报告 `unpersisted`，但仍正常结束。问题很多不是继续对齐的理由；只要剩余问题不会推翻成功边界，就停止追问。

## 编码 Gate 与交接

- 用户只要求对齐：不得修改产品代码；输出 ready / blocked、spec 位置、残余风险和下一动作。
- 用户已对当前 active goal 和当前 scope 明确要求“对齐后直接实现”：ready 后无需追加仪式性确认，交给 `to-implement`；范围发生实质变化时重新判断授权。
- 用户在对齐中明确说“开始落实 / 开始编码”：先确认停止条件；未 ready 时只说明当前唯一 blocker，不带着产品口径空缺开工。
- 实现中发现规范性冲突或新的人类决策：暂停相关代码，返回 `to-align`；普通局部工程选择继续由 runtime 处理。

## Self-Review

- 是否覆盖了用户每一项原始要求，而不是只讨论最显眼的部分。
- 是否先查仓库事实，并正确区分人类、Agent、runtime 与外部 authority。
- 是否每轮只推进会解锁下游的实质问题。
- 是否因理论边角扩大 scope 或恢复复杂度，违反 ROI。
- spec 是否只保存稳定结论，没有问题树、问答流水或实现拓扑。
- ready 后的交接是否符合用户已有授权，没有多加或跳过编码 gate。
