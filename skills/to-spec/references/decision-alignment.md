# 深度决策对齐

本参考只在复杂或高风险设计中按需加载。目标是找到会改变整体设计的少数根决策，而不是扩大提问数量。

## 1. 建立因果底座

先用仓库证据和用户语境回答：

- 当前行为为何不足，直接症状与根问题分别是什么。
- 哪个可观察结果必须改变，哪些现有能力必须保持。
- 谁拥有输入、状态、裁决和验收权。
- 哪些跨系统、数据、权限或外部契约形成硬边界。
- 如果什么都不做，真实代价是什么。

不能从证据支持的内容标为未知；不要把猜测伪装成事实。

## 2. 找出实质分叉

对每个候选问题做反事实检查：如果选另一个答案，下列内容是否会改变？

- 成功 / 失败定义
- 用户或外部系统可观察行为
- 状态所有权、数据语义或一致性模型
- 权限、隐私、安全或审计边界
- 兼容、迁移、回滚或不可逆风险
- 重大 scope、成本或验收方式

全部不改变时，它通常是 Agent 决策或 runtime 选择，不应打断用户。

## 3. 沿依赖顺序推进

在对话中临时维护依赖关系即可：

1. 找出能关闭最多下游分叉的根问题。
2. 先取证，排除可由仓库回答的部分。
3. Agent 有权限决定时直接判断，并说明核心依据。
4. 必须由用户决定时，一次只问一个。
5. 回答后重新计算仍真实存在的前沿。

不要把这棵树、已关闭分支或问答顺序写入 spec。

## 4. 高价值提问格式

问题应短，但上下文必须足够：

```text
需要你决定：<一个明确分叉>
我的建议：<推荐选项>，因为 <最关键理由>。
主要影响：<其他选择会改变的行为、风险或成本>。
这会解锁：<回答后能够稳定确认的下游设计>。
```

有真实离散选项时给 2-3 个互斥选择；开放探索更合适时不要硬造选择题。推荐不是替用户决定，而是暴露 Agent 当前判断，减少无效往返。

## 5. 分段校准

复杂设计不要等整份 spec 写完才对齐。建议按以下语义块逐段确认：

1. 根问题、成功边界和非目标。
2. 系统边界、状态 / 决策所有权和关键契约。
3. 正常路径、边界路径和反例路径。
4. 迁移、风险、验证意图与残余开放问题。

每段只校准会影响后续设计的内容。措辞、排版和普通实现细节由 Agent 自行处理。

## 6. 压力检查

- 反例：什么输入或状态最容易推翻当前结论。
- 权威冲突：多个来源不一致时谁拥有最终裁决权。
- 失败恢复：部分成功、重试、回滚或超时后不变量是否仍成立。
- 时间边界：旧数据、并发更新、版本切换或延迟是否改变语义。
- 滥用路径：权限提升、错误身份、越权数据或不可逆操作如何被阻止。
- 可验收性：证据能否区分“实现了”与“看起来实现了”。

只把压力检查产生的稳定需求、决策、风险或阻塞写回 spec，不记录检查流水。

## 7. 停止条件

满足以下条件即可停止追问并形成就绪证明：

- 剩余未知不会改变已确认的成功边界和关键契约，或已有明确外部解除条件。
- 人类拥有的实质决策都已确认。
- Agent 拥有的设计选择已有足够证据，可在已确认边界内自主完成。
- runtime 选择仍留给执行时判断。
- 实现与验收都不需要猜测核心产品 / 数据 / 权限口径。

问题数量不是质量指标；用最少问题关闭最大的决策不确定性才是目标。
